# HH520 Stable V3.2 整改问题清单与验证原则 V1.0

更新时间：2026-09-22  
状态：已冻结为下一轮统一整改基线  
适用对象：HH520 Stable V3.2 / Research Lab  
原则：先验证可行性，再修改 Stable；未经历史验证与冻结后验证，不晋升正式模型。

---

## 一、用户提出的 8 个必须整改问题

### 1. 正式输出字段过多
当前正式输出包含：
- 球队对阵
- 胜平负
- 市场概率
- 置信等级
- 比分×2
- 半全场×2
- 总进球
- 置信度
- 最终筛选

用户要求正式展示删除：
- 置信等级
- 置信度
- 最终筛选

目标正式输出核心字段：
- 球队对阵
- 胜平负
- 市场概率
- 比分×2
- 半全场×2
- 总进球

说明：此项属于输出层整改，不需要重新训练模型，但需要验证输出契约与 GPT Action 一致。

---

### 2. 胜平负不能只机械取最高市场概率
当前 V3.2 的 WDL 正式方向来自 1X2 市场赔率去水概率，并直接取 argmax。

问题示例：
- 主胜仅约 42%，仍直接输出“主胜”
- 剩余概率分散在平局与客胜，说明方向并不集中
- 历史研究中已经存在 Balanced / Draw 风险结构，当前正式方向没有真正使用

整改目标：
- 重新验证 Balanced / Draw 分支
- 找出 pmax、第一第二概率差（margin）、平局概率等阈值
- 低集中度比赛不能机械取最大概率
- 需要明确区分：强方向 / Balanced / Draw-risk / Tail-risk

必须用 2026-05-01 至 2026-09-20 历史数据重新验证。

---

### 3. 半全场、比分、总进球缺少概率参照
当前：
- 胜平负有市场概率
- 半全场只给结果
- 比分只给结果
- 总进球只给结果

整改目标：
- 胜平负：显示市场去水概率
- 半全场：显示 HTFT 模型概率
- 比分：显示比分模型概率
- 总进球：显示总进球模型概率
- 后续增加历史校准率（模型给 20%，历史同类是否真的约 20%）

此项需要验证概率字段完整性与概率校准，不一定需要重训。

---

### 4. 胜平负 → 半全场 → 比分缺少方向一致性
当前 HTFT 将 9 种半全场组合独立排序，Score 又独立排序。

会出现：
- 胜平负 = 主胜 42%
- 半全场 Top2 = 主/主 + 客/客

数学上可以成立，但用户看到的最终预测逻辑互相冲突。

整改目标：
- 建立跨层一致性机制
- 先识别比赛结构：强主 / 强客 / Draw / Balanced / Tail
- 半全场必须与比赛结构保持逻辑一致
- 比分必须与 WDL、HTFT、总进球方向相容
- Balanced / Tail 场允许保留反向场景，但必须明确标记为“尾部场景”，不能与主预测混在一起

必须用历史数据验证“有一致性约束”是否比“各模块独立 Top-K”更好。

---

### 5. 正式模型缺少尾部高赔 / 爆冷分支
历史回测（2026-05 至 2026-09）中有相当一部分比赛属于尾部高赔、反市场、爆冷结果，但 Stable V3.2 正式链路没有独立 Tail 分支。

整改目标：
- 重建 Tail / Upset 模块
- 识别：热门失效、低概率平局、高赔客胜、高赔主胜
- 不允许简单按“赔率高”选尾部
- 必须验证哪些赔率区间、概率分散、基本面冲突、盘口结构与 Tail Winner 有稳定关系
- 主预测与尾部备选必须分开显示

必须用 5–9 月历史数据做可行性审计，再用冻结后新数据做 Shadow / Forward 验证。

---

### 6. 半全场缺少球队分时段进球/失球数据
当前 HTFT 模型实质为：

P(HT,FT) = P(FT) × P(HT | FT)

其中 P(HT | FT) 是固定历史条件矩阵，没有使用球队自身的进球/失球时间结构。

缺失的核心数据：
- 0–15 分钟进球 / 失球
- 16–30
- 31–45
- 46–60
- 61–75
- 76–90
- 上半场进球率 / 失球率
- 下半场进球率 / 失球率
- 最好区分主场 / 客场
- 最好支持近20场 / 近50场滚动窗口

已确认可行的数据思路：
- SoccerSTATS 等公开源可提供部分联赛的 15 分钟进失球分布
- 长期更稳定方案：基于逐场“进球分钟事件”自行重建滚动分布
- 历史回测必须只使用当时日期之前的数据，避免赛后污染

整改目标：
- 建立独立半场模型 P(HT)
- 再与全场模型结合得到 9 种 HTFT 联合概率
- 不再仅依赖固定 P(HT|FT) 矩阵

必须先补历史分时段数据后才能正式验证。

---

### 7. 胜平负缺少“反市场保险机制”
当前正式 WDL：
- 市场赔率去水
- argmax 决定方向
- pmax >= 0.73 只是高置信门槛

现有机制只能判断“市场是否足够强”，不能判断“市场方向是不是错的”。

历史回测中存在：
- 市场热门失败
- 市场方向与真实赛果相反
- 平局被市场低估
- 基本面与市场方向明显冲突

整改目标：
建立独立 Market Conflict / Override 校验层，用于判断：
- 市场方向可信
- 市场方向弱
- 市场与基本面冲突
- 需要降级
- 需要转入 Draw / Balanced
- 需要转入 Tail / Upset 分支
- 是否存在足够证据允许反市场

注意：不能为了反市场而反市场。任何 Override 规则必须在历史数据上优于等条件市场基线。

---

### 8. 比分模型过度集中在低比分
当前 Score 使用 Pooled Poisson，Top2 经常集中在：
- 0:1
- 1:0
- 1:1
- 2:0
- 2:1

导致 3:1、4:1、3:4、4:2 等高比分很难进入候选。

整改目标：
- 验证高总进球 / 高方差比赛识别
- 验证 Negative Binomial / Over-dispersion 等高方差模型
- 验证联赛高比分系数
- 验证球队极端进攻/防守放大
- 验证总进球市场或节奏信息
- 增加“尾部比分候选”，但不能为了显示大比分而制造噪声

必须比较当前 Pooled Poisson 与候选模型的 Top1/Top2/Top3/Top5、NLL，以及高比分样本召回率。

## 二、进一步发现的结构问题

### A. Value Layer 目前缺乏真正独立的信息
当前正式 probability 本身就是市场去水概率，而 Value Layer 又计算：

模型概率 - 市场基线

如果两者来源相同，edge 天然接近 0。

整改方向：
- 只有建立真正独立的模型概率后，Value Layer 才有意义
- 否则应明确它只是审计层，不得假装存在独立价值信号

---

### B. Decision Filter 当前真正生效的规则过于单一
当前正式决策核心几乎只有：

market pmax >= 0.73

Risk / team factors / odds conflict 目前基本是 advisory，不能真正改变方向。

整改方向：
- 将 Decision Filter 从“强度门槛”升级为“结构验证层”
- 但所有新增规则必须通过历史验证与冻结后验证

---

### C. 缺少概率校准 Calibration
需要验证：
- 模型说 10% 的比分，历史是否约 10% 兑现
- 模型说 30% 的 HTFT，历史是否约 30% 兑现
- 不仅看排序，还要看概率是否可信

建议：
- Reliability curve
- Brier / Logloss / RPS
- 分桶实际兑现率

---

### D. 缺少跨层概率守恒 / 一致性审计
未来应检查：
- Score matrix 汇总出的 WDL 是否与最终 WDL 严重冲突
- HTFT 汇总出的 FT 概率是否与 WDL 严重冲突
- Score matrix 汇总出的总进球分布是否与 Total Goals 层冲突

冲突严重时必须：
- 降级
- 标记冲突
- 或重新选择候选

---

### E. 数据新鲜度机制不足
当前同日期缓存不会自动更新。

风险：
- 上午赔率与下午临场赔率可能已经明显变化
- 预测仍使用旧缓存

整改方向：
- 历史缓存继续固定
- 比赛日前预测增加 timestamp / freshness
- 必要时允许手动或规则化刷新
- 不允许在不知数据时间的情况下把旧盘口当实时盘口

---

### F. 数据质量门禁需要加强
除现有赔率、球队、联赛检查外，还应检查：
- 攻击/防守/交锋/状态是否缺失
- 8 个球队模块是否全部 0
- possession 是否缺失
- 分时段数据是否缺失
- 数据是否过旧
- 盘口文本是否异常
- 历史数据是否存在赛后污染

---

### G. 主预测与尾部备选必须分层
未来输出不能把：
- 主预测
- 爆冷候选
- Draw-risk
混成同一级别。

建议结构：
- 主场景
- 次场景
- Tail / Upset 场景（只有达到条件才显示）
- 每个场景附对应概率与触发原因

## 三、验证原则

### 1. 先验证，再改 Stable
8 个问题中：
- #1 输出删列：不需要模型回测
- #3 概率展示：主要做概率完整性与校准验证
- #2/#4/#5/#6/#7/#8：必须做历史验证

### 2. 开发窗口
可使用：
- 2026-05-01 至 2026-09-20

用途：
- 找规律
- 找阈值
- 比较候选公式
- 可行性审计

这些数据已经多次参与开发，因此不得再包装成 untouched final validation。

### 3. 最终晋升
任何 Candidate Rule 若要进入 Stable：
- 必须冻结规则
- 使用 2026-09-21 之后未参与开发的数据做 Shadow / Forward 验证
- 不允许自动晋升
- 必须人工审核

### 4. 基准
WDL：
- 必须始终与去水市场基线比较
- Accuracy 之外必须看 Logloss / Brier / RPS

HTFT：
- Top1 / Top2 / Top3
- Logloss

Score：
- Top1 / Top2 / Top3 / Top5
- NLL
- 高比分样本召回率

Tail：
- Tail coverage
- Tail precision
- Tail winner recall
- 与同赔率区间/同市场强度基线比较

### 5. 禁止事项
- 不允许赛后数据污染
- 不允许用真实赛果反推同场预测输入
- 不允许为了提高历史命中率无限加规则
- 不允许只看 Accuracy
- 不允许无验证直接覆盖 Stable V3.2
- 不允许 GPT 自行修改冻结预测结果
